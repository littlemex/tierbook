## Why

CONTRACT.md はこのリリースを一文で述べている: まずログが自分自身の進化を生き延びるようにし、その上で安全に探索へ入る、という順序である。v0.1.0 はループを一巡させたが、そのループが書いた記録は自分自身のスキーマ変更を生き延びられなかった——`Decision` にフィールドを一つ追加するだけで、`Log.read` 自身の破損行トレランスの外側で、既存の読み手が全ての行で例外を投げるようになり、スキーマ変更はカウントされる対象ではなく acceptance の走行全体を殺すものになっていた。そして、決定的な候補以外へトラフィックを振る仕組みは何も無かった: v0.1.0 自身のリリース文書は「変動するロギング済みの選択確率」と「探索またはシャドウ割り当て」を最も本質的な欠落として名指ししていた。決定論的なポリシーが下すすべての決定は propensity が 1 であり、その下では反事実側のアームにデータが存在せず、オフポリシー推定は識別不能になるからである。本リリースが最初の欠落を閉じるのは、下の形が変わりうるアーティファクトの上に二番目を積むことはできないからであり、その上でようやく探索を有効にする。

## 変更内容

**ログはフィールドが増えても生き延びる。** `record.from_row` が `accept._as_decision` の `Decision(**kw)` という展開処理を置き換える。行が持つ未知のキーは無視されるが名前を残して報告され、`schema_version` が読み手の知る範囲を超える行は無条件に解釈されるのではなく名前を挙げて拒否され、そのバージョンが要求するフィールドを欠く行は `Incomplete` がそのフィールド名を挙げて例外を投げる。バージョンが一切無い行はバージョン 1 として読まれる。それは誰にも強制されない慣習によってではなく、読み手自身のコードによってである。同じ扱いが candidate 行の未知キーにも位置つきで及ぶ。監査の結果、`bound_n`/`bound_attempted` がそもそも candidate 単位のフィールドであり将来のエントリが置き換える可能性があると分かったが、当初の設計は decision 行しか名指ししていなかったためである。このリーダーと並んで、構造的な欠落が二つ閉じられている。閉じた語彙 `EXCLUSION_REASONS` は自分自身に対してしか検査されておらず、9 個の値を一つずつ削除してスイート全体を流すと、`not_authorised`、`latency_infeasible`、`unavailable`、`no_bound` の 4 つはスイートに一切カバーされていないことが分かった。つまり `record.admissible` と `serve._why_not` は、`Candidate.__post_init__` が拒否するはずの文字列を、どのテストも通らない経路上で本番で返しうる状態だった。修正では語彙を自分自身の第二のリストに対して検査するのではなく、語彙を生成する側の関数を検査するようにした。そして `from_row` が返す ignored キーのリストは誰にも届いていなかった: `Log.read` と `accept` の 3 箇所すべてがこの値を捨てていた。新しい仕組みが記録した propensity や eligible_set といったフィールドが、より古いリーダーに黙って消えているにもかかわらず、リーダーが自分のログより後れていることを示す信号は無かった。`Log.read` は今 `__ignored_keys__` を名前つきで持ち、`accept` のレポートもこれを記録する。

**ポリシーがコンパイルされた際のパラメータには、記録される場所が一つになった。** 本リリース以前、コンパイル済みアーティファクトは `certified: true` を持つがそれが証明された floor を持たなかった。floor には CLI の `assign`、`serve.route_once`、`accept` という 3 つの供給点があり、記録されたコピーは 0 個だった。ログに対して計算されるどの基準も、ポリシー自身の floor を使ったと確認できる保証が無かった。floor がコンパイルパスのどこに入るのかを追ってそこから運ぶ、という当初の調査方針は、floor がどこにも入っていないという事実に行き着いた。config と schema のファイルを `grep floor` しても何も出ず、objective の constraints には相対的な non-inferiority のマージンしか無い。floor はこのリポジトリのどこにも一度も宣言されていなかったので、記録すべき最初のコピー自体が存在しなかった。floor は今、family 単位の宣言になっている——`families` は名前を裸の reference candidate 文字列に対応させるマッピングであることをやめ、`reference` と `floor` を持つオブジェクトになり、`config_format` は 1 から 2 になり、裸の文字列は何を変えるべきか名指しして拒否される。これは SCOPE が floor をレビュー可能でバージョン管理されたファイルの一行と呼んでいるためであり、また floor は family 単位のものであって、単一の `compile --floor` フラグ(実装され、公開前に取り下げられた)には表現できないためである。異なる精度要件を持つ 2 つの family が、たまたま入力された一つの数値を黙って共有してしまう。`decide.Policy.parameters` は今 floor、`max_evidence_age_days`、`staleness_limit_days` を持ち、`decide.parameter(policy, name, supplied=None)` が唯一の読み手になる。何も渡されなければアーティファクトの値を返し、渡された値がアーティファクトと等しければそれを返し、異なればどちらか一方を優先するのではなく両方を名指しして例外を投げ、アーティファクトが一度も記録していない名前に値が渡されればそこでも例外を投げる。`assign --floor` と `accept --floor` は今どちらも省略可能で、アーティファクトと不一致であれば終了コード 4、`accept` は `--policy` を新たに受け取り、`--policy` と `--floor` のどちらも与えられなければ終了コード 2——argparse 自身が「必須の引数が与えられなかった」場合に使うコードであり、コード 4 とは別に保たれているのは、この二つの失敗がオペレータに求める行動が異なるからである。falsifier が照合する freshness の上限にも同じ扱いが同じ理由で及んでいる: `accept` のレポートは今 `max_age_days` とその provenance の行を持つ。`--policy` を与えずに実行した走行は、admissibility の 4 条件のうち 3 条件しか確認しておらず、そのレポートはこれまでどの 3 条件を確認したのかについて誠実ではなかったからである。

**family は誰が自分にラベルを付けるかを宣言し、使えるラベラーが無ければ探索レートも持てない。** `Log.attach_outcome` は存在するが誰も呼ばない。その上に探索を積めば、誰も学習に使えないランダム化された割り当てが生まれるだけなので、この結合は付随物ではなく前提条件である。各 family は今、floor が住んでいるのと同じ family 単位のオブジェクトの中で `label_source`、`max_label_latency_s`、`label_independent_of_candidate` を宣言する。`label_source` は tier record 自身の `oracle.kind` の列挙値をそのまま使い、そこに `none` を一つだけ加えたもので、コピーではなく schema ファイルから直接読むため二つの列挙が食い違うことがない。この項目の初期の草案は、この宣言を将来の要求が判定される config ではなく計測用の schema に置いていたが、それではこの第二の粗い語彙が生まれてしまう。`label_independent_of_candidate` が存在するのは、自分自身も family 内の candidate であるジャッジは、構造的にその candidate を完璧な点数で採点してしまうためであり、tier record はオフラインの経路でこの条件を既に強制しているのに、オンラインの宣言はそれを黙って落としてしまうところだった。`exploration_rate` は `label_source != "none"` かつ `label_independent_of_candidate` が真である場合にのみ family に付けられ、そうでなければ `load_config` はそのレートと理由の両方を名指しして拒否する。この拒否はロード時の失敗であり実行時の発見ではない——アーティファクトはその欠けた組み合わせをそもそも表現できず、何かが実行時に気づくことを期待する形ではない。`record.classify_label(decided_at, now, max_label_latency_s, label)` はこれらの宣言を `labelled` / `pending` / `missing` に変換し、`Log.read` は `schema_version` が 2 未満の行を再分類しない。古い outcome は、それが書かれた当時支配していなかった latency のルールのもとで黙って書き換えられるのではなく、書かれた当時のラベル状態を保持する。

**探索: 適格集合・draw・記録された propensity、そして certification が実際にどこから来るか。** `explore.clears_floor` は `admissible` から分離されている。`admissible` は bound を比較する前に expiry を判定するため、`admissible` を再利用すると freshness のラチェットがロックアウトしたアームに到達できない——探索が必要とする唯一の抜け道であり、選ばれないアームは決してラベル付けされないからである。それ以外の除外理由はすべてそのまま効く: `not_authorised`、`latency_infeasible`、`unavailable`、`not_priced`、`no_bound` のいずれかに該当する candidate は探索対象にならない。適格集合を列挙できないランダマイザに有料トラフィックを通すのは、スキップしてよい拒否ではないからである。1 回の決定につき draw は 1 回だけ行われ、記録される propensity は実際に行われた draw の下で実際に選ばれたアームの条件付き確率である。レート 0.05・代替アーム 1 個の場合、既定アームは 0.95、代替アームは 0.05 になる。初期の草案自身の例が誤って 0.95/0.025 としていたのとは異なる。この仕組みに到達する過程で、実装される前に SCOPE 自体の欠陥が露呈した: `explore.clears_floor` は family 自身の上限を超えて古い evidence でも eligible を返せる——これがそもそもこの抜け道の目的である——一方で `record.admissible` の第 4 条件である freshness は同じ candidate に対して独立に `evidence_expired` を返し、falsifier は探索がまさに作り出そうとしているそのケースの割り当てを `certified` として報告していた。SCOPE 2 節は admissibility の条件を 3 つと名指ししていたが、コードは v0.1.0 以来 4 つを強制していた。文書は 4 つ目を名指しするよう修正され、`serve.route_once` は今、探索されたかどうかに関わらずすべての割り当てについて、freshness を含む完全な admissibility から `certified` を導く。抜け道を通って到達したアームは今もサーブされる——ラベルは戻ってくるし evidence も更新される。これこそがその抜け道を開いた理由である——ただ、その bound を支える evidence が古いあいだは certified とはみなされない。`floor_compliance` は SCOPE 12 節の 9 個という数に合わせて 1 個の基準のままだが、その `numbers` の中で `certified` と `all_served` という 2 つのレート、それぞれ独自の bound と sub-verdict を報告し、両者のうち悪い方を自身の verdict として採用する。片方が pass でもう片方が fail であれば、それは pass として提示されない。

**レート系の基準はスキーマバージョンが混在したログを pool しない。** 探索が存在するようになったことで、バージョン境界で黙って変化する数値が 6 つある: 探索の share はログの長さで薄められ振る舞いでは薄まらない、default の propensity が 1 の行が加重推定にとって無限の重みを持つ確信として混入する、など。`accept.check_all` は `pool_across_versions: bool = False` を新たに受け取り、ログが複数の `schema_version` にまたがり pooling が要求されていなければ、`floor_compliance`、`default_is_not_a_hiding_place`、`exploration_cost`、`spend_regret` は存在するバージョンとそれぞれの件数を名指しして `UNSUPPORTED` を返す。一方 `no_false_certification` はこの影響を受けず計算される。これは比率ではなく決定ごとの普遍的な主張であり、混在によって意味が変わるものではないからである。このガードは各基準が計算を終えた後に適用され、計算の前ではない。そのため `PASS` か `FAIL` だけを上書きし、基準自身が出したより具体的な `UNSUPPORTED` を上書きしない。まだ実装が無いという基準の「実装がありません」と「ログが 2 つのバージョンを混在させています」はオペレータにとって異なる対応を意味する。ガードを先に適用すると前者が黙って後者に置き換わってしまうことが判明した。

**実際の ledger のアップグレードは 6 回のロードではなく 2 回で済むようになった。** `load_config` はこれまで最初に出会った family の問題で例外を投げて止まっていた。このプロジェクト自身が公開している v0.1.0 の candidate ファイルで測ると、それは 5 回の連続した——それぞれ単体では正しい——拒否だった。1 回のロードにつき 1 個の問題が見つかる形である。今は family 全体のすべての問題を一つの `ConfigError` に集めて一度だけ例外を投げ、往復回数そのものも aggregation とは別にアサートされる。5 件のうち 2 件だけを列挙するメッセージでは、すべてを列挙するというテストを通過できない。

## 2 つの破壊的変更と、それぞれの実測された移行コスト

**`config_format` は 1 から 2 へ移る。** `families` は名前を裸の reference candidate 文字列に対応させることをやめ、`reference`、`floor`、そして(上記のラベラー宣言・探索のエントリが、バージョンを再度上げることなく追加した)`label_source`、`max_label_latency_s`、`label_independent_of_candidate`、`staleness_limit_days` を持つオブジェクトになる。現行より古いフォーマットは全面的に検証される——両方の形が既知であり、その差こそがオペレータに伝えるべきことそのものだからである——一方、現行より新しいフォーマットはどの family も検査せずバージョンだけで拒否される。読み手が知らない形は、読み手が知っている形と意味のある比較ができないからである。このプロジェクト自身の v0.1.0 の candidate ファイルで測ると、上記のロード集約の修正前は移行に 6 回のロードが必要だった: バージョン、最初の family の形、その family が欠く 4 つのキー、2 番目の family、と 1 回のロードにつき 1 個の問題が見つかる形である。修正後は 2 回で済む: すべての family のすべての問題を名指しした 1 つのメッセージ、その後の 1 回のクリーンなロードである。形を名指しするメッセージは今、その形全体を名指しする。かつては 2 つのキーしか挙げていなかったメッセージを信じて `{"reference": ..., "floor": ...}` だけを直した operator は、それまで一言も告げられていなかった残り 4 つのキーを名指しする二度目の拒否を受け取っていた。それだけで元の 6 回のうち 4 回を占めていた。

**decision record の `schema_version` は 1 から 2 へ移る。** この方向にはまったく移行が要らない。`schema_version` の無い行はバージョン 1 として、黙って、エラーなく読まれる。`record.from_row` はこのプロジェクト自身の v0.1.0 の decision log を、何も例外を投げず何も失わずに読む。v0.1.0 の行が持つすべてのフィールドは、バージョン 1 の形が知っているフィールドである。2 つの破壊的変更は意図的に正反対に扱われている。config のフォーマットは全面的に検証される。両方の形が既知であり、オペレータが編集する文書であり完全に伝えられる必要があるからである。decision log の古い行はそれが常にそうであった通りに読まれる。過去の決定は、より新しいツールで読まれることによって何も変わらないからである。

## 本リリースが自分自身に見つけた欠陥

### アーティファクトは既に出荷済みの 3 つの事柄を「欠けている」と主張するリストを、テストがそう主張し続けるよう要求したまま出荷していた

`decide.MISSING_FOR_A_CLOSED_LOOP` は、コンパイル済みポリシーのアーティファクトすべてに `missing_for_a_closed_loop` として書き込まれる 6 項目のタプルであり、「その不在が存在と誤認されないように」という説明を持つ。本リリース自身の `HEAD` で、6 項目のうち 3 つは偽だった: 状態のコレクタは 1 リリース分ずっと偽であり、v0.1.0 で `observe.py` として既に出荷されていて、v0.1.0 自身のリリース文書は「このタプルは最初の 1 項目を閉じる」と述べたままこの項目を一度も削除していなかった。変動するロギング済みの選択確率、そして探索そのものは、本リリース自身の探索機構が出荷された瞬間に偽になった。`Decision.selection_probability` は変動しているし `explore.py` は存在する。`tests/test_decide.py::test_the_artifact_names_what_a_closed_loop_still_needs` は、出荷されるアーティファクトが探索と変動する propensity を「欠けている」と主張し続けることを要求していて、本リリースの先行するすべてのエントリの diff がこのタプルに触れなかったためにそれらすべてを通過していた。これを見逃していたガードは、タプルのテキストの中に 4 つの部分文字列が存在することだけを検査していた。何らかの機構を追加することは、その機構の不在が主張され続けていることだけを見るチェックを失敗させない。これは上記の enum-membership の欠陥と同じ形で、構造的に見えないようになっていた。出荷済みの 3 項目は削除され、残るすべての主張——anytime-valid bound、change-point 検知、予約候補の希少キャパシティに対する値——は今それぞれ probe に結び付けられている。probe とは、その主張を反証しうるシンボルやモジュールを名指しする callable であり、すべての主張とその probe が一致することをテストがアサートする。probe を書けない主張は、機械可読なアーティファクトに載せるには曖昧すぎる主張である。

### 探索は「ランダマイザが走った」ことを記録していて、「トラフィックが振られた」ことを記録していなかった

`explore.draw` は能動的な draw の 2 つの結果——代替アームが勝つ場合と、既定アームがそれでも勝つ場合——のどちらにも理由として `"explored"` を返していて、`serve.route_once` はその文字列だけから `exploration` フィールドを設定していた。レート 0.05 で 5,000 シードにわたって測定すると、理由が `explored` になるのは draw の 100.0% で、実際に代替アームへ振られたのは 5.52% だけだった。`accept.exploration_cost` はこのフィールドから直接 share を計算していたため、実際には 25% の予算に対して 5.52% しか使っていない機構に対して、探索の share を 100% と報告していた。予算の内側でうまく動いている機構を失敗と報告する基準は、上記の freshness ラチェットの修正が回復のために依存している探索そのものを、オペレータに縮小・停止させる圧力になる。このフィールドがこの区別を表現できなかった理由は、その語彙が 1 つ足りなかったことにある。`exploration_reason` は既に「機構が無い」「適格集合が空」「レートがゼロ」という 1 ビットを共有する 3 つの原因を区別していて、そこに 4 つ目、「ランダマイザは走ったが既定アームが勝った」を表す `not_diverted` が加わった。`exploration` は今、`route_once` がすでに 3 行先で計算していた信号である `chosen != deterministic` として導出される。propensity は変わらない。能動的な draw のもとで既定アームが勝っても、その propensity は 1 ではなく `1 - rate` のままである。propensity と diversion のフラグは異なる問いに答えている——一方はオフポリシー識別のため、もう一方は予算の会計のためであり、この 2 つを混同したことがこの欠陥を生んだ。

### レート系の基準は、本リリース自身が区別できるようにしたはずの行を、まさにその分だけ母集団から除外していた

`accept._unreadable` は `outcomes["__bad_lines__"]` だけを読み、この同じリリースのリーダーが JSON としては解釈できるが `from_row` に失敗する行——リーダーが知らないバージョン、行が欠くフィールド——のために追加した `__unreadable_rows__` というカウンタを一度も読んでいなかった。40 件のラベル付き成功と、読めないバージョンを刻んだ(すべて失敗としてラベル付けされるはずの)15 行で再現すると、`floor_compliance` は `pass`、レート 1.0、下限 0.9278 を報告するが、落とされた行を数えた真のレートは 0.7273 であり、これは 80% の floor に対して fail する。これは、この基準自身が certified トラフィックと all-served トラフィックの分母について既に持っていたのと同じ形の問題であり、本リリース自身が導入したカテゴリに対して同じガードを拡張していなかっただけである。今は 2 つの読めない行のクラスがそれぞれ別々に数えられ名指しされ、`default_is_not_a_hiding_place` はこれまで一切受け取っていなかった `outcomes` パラメータを新たに受け取る。これが、これまでどちらのクラスに対してもガードを持っていなかった理由である。

### bound を計算する関数は、試行数より多い成功数を受け取り、確信を持って答えていた

`accept.clopper_pearson_lower(n, k, alpha)` は、このプロジェクトのすべての floor 判定が依拠する下側信頼限界を計算する。その境界条件 `if k >= n: return alpha ** (1.0 / n)` は `k == n` では正しいが `k > n` にも同様に適用されていた——これは境界ではなく矛盾である——そのため 16 回の試行に対して 20 回の成功が記録されたケースで `0.8293` が返り、そのまま採用されていた。この誤差は高い方向に出るため、候補を実態より良く見せる。これは下記の C13 を調査している最中に、サンプル ledger の `self-hosted-a` という tier が、引数を入れ違えた `0.8293` という値で 0.80 の floor をクリアしていると読んでしまったことで見つかった。この tier の真の bound は `0.4922` である。`k > n` は今、両方の数値を名指しして例外を投げる。`n <= 0` は以前は `alpha ** (1.0 / 0)` に到達して名前の無い `ZeroDivisionError` で落ちていたが、今は明示されたエラーを投げる。

## phase 5 が確立したこと、そして確立しなかったこと

phase 5 は `g5.xlarge` を 1 台立て、20 並列の負荷のもとで `Qwen/Qwen2.5-0.5B-Instruct` を動かす vLLM 0.29.0 に対して機構を走らせ、その後インスタンスを破棄した。確立されたこと: `observe` は定数を返しているのではなく occupancy を読んでいる——400 サンプルにわたって `inflight` は 2 から 20 まで 19 種類の異なる値を取った。これは 1 回の観測では示せないことである。定数は、値が動くまで計測とは区別できないからである。エンジンがサーブしていないモデルを尋ねると、`observe` はそのモデルのメトリクスとラベル集合を名指しして変数が absent であると報告する。idle なエンジンとして読まれてしまうゼロへのデフォルトは行わない。文書化された経路は順番に走る——`validate`、`compile`、`observe`、レートを得るための `observe --previous`——そして `accept --policy` は照合した floor(0.8)と evidence-age の上限(90)を、それぞれアーティファクトを名指しする provenance の行つきで記録する。`ignored_keys` は空である。この走行のリーダーは目にしたすべてのフィールドを理解していたからである。記録されるラベルは「エンジンが空でない completion を返したかどうか」であり、タスクの成功ではない。レポートはそのことを述べており、誰も計測していない成功の信号を勝手に取り付けたりはしない。別途、7 件の contract エントリ——C5、C6、C8、C9、C10、C11、C12——それぞれが修正前のコミットで再現され `HEAD` で解消していることが再確認されている。これが上の表の「検証」欄の根拠である。

確立されなかったこと: 探索の実際の挙動である。400 件の実際の決定にわたって、draw は 0.05 というレートが宣言されているにもかかわらず毎回 `no_eligible_arm` を返し、diverted な share は 0 だった。`serve.candidate_set` はポリシー自身の rule と default から適格集合を構築するが、サンプル ledger からコンパイルされたポリシーは rule を一つも持たない——コンパイラは 20 件のコホートに対してその family のいかなる candidate も certify しなかった——ので適格集合はメンバーが 1 つしかなく、draw は毎回正しく辞退している。これはこのフィクスチャに対しては正しい挙動であり、draw そのものについての証拠にはならない。certify された rule を一つも持たないポリシーが、その rule の集合を超えて探索を及ばせるべきだったかどうかは、この走行が答える設計上の問いではない。held-out fold が拒否した candidate へ有料トラフィックを流すことは、まさにコンパイラの拒否が防ぐことになっている事態だからである。draw の算術は別途、5,000 シードにわたるレート 0.05 のもとで hermetically に検証されており、上で用いた 5.52% という数値を再現している。そして C13 は修正されていない: caller は今も evidence が支持しない bound を主張でき、`no_false_certification` はそれを通す。falsifier が admissibility を計算する際、アーティファクトが記録した何かではなく caller 自身の数値を使うからである。

## C13 は見送られている。その理由

C13 は、`route_once` が floor と比較する bound を、caller が渡す何かからではなく、floor 自身に対して amendment 2 が確立した規則と同じ形でアーティファクトから読むよう求めていた。実装しようとして分かったのは、アーティファクトが渡すべき量そのものを持っていないということだった。`policy.assign_family` の `ranked` が持つ `quality_lcb` は、reference tier との**差**に対する対のついた下側 bound であり——サンプル ledger の `self-hosted-a` では `-0.469`——SCOPE 2 節 1 項が求めているのは絶対的な下側 bound であり、コンパイラはこれを一度も計算していない。これを導出することは可能で、このパッケージに既にある正確な bound の関数を各 tier 自身の `solved`/`attempted` の対に適用すればよいが、それは単に数値を読む場所を変えるのではなく、コンパイル済みポリシーが主張する内容そのものを変える: サンプル ledger で 0.80 の floor に対して計算すると、floor をクリアするのは reference tier だけである(`api-cheap-a` は 16/20 → 0.5990、`api-strong-a` は 20/20 → 0.8609、`self-hosted-a` は 14/20 → 0.4922)——このプロジェクトの README 自身が、20 件のコホートは信用するには小さすぎると既に述べている規模である。既に 13 個のエントリを重ねたリリースの最後にこの変更を吸収することは、進行中のすべてと並行してコンパイル済みポリシーが主張する内容そのものを再設計することを意味し、サンプル ledger 自身の答えがその副作用として変わってしまう。それはリリースが欠陥を修正する形ではなく、誰にもレビューされない欠陥を獲得する形である。C13 はこの観測結果を入力として次のリリースの最初の phase へ引き継がれる。含みを持たせず明言しておく: caller は evidence が支持しない bound を今も主張でき、falsifier は caller 自身の数値から admissibility を計算するために、それをそのまま通す。

## 本リリースにはこれも含まれている

`harness/tests` の 4 つのテストは、stall タイマーにリテラルの `0.0` を種として与え、それを言語仕様上参照エポックが定義されていない `time.perf_counter()` と比較していた。これが見つかったマシン上では、Python 3.9 ではプロセス起動時刻、3.11 ではブート時刻であり、その差は 803,137 秒あり、1 行も解釈する前に 2,400 秒の stall ceiling を超えてしまっていた。この 4 つのテストは同じコミットのまま 3.9 では成功し 3.11 では失敗していた。本番のコードは既に正しく、両方の読みを `perf_counter()` 自身から取っていた。値をどの時計からも取らずに与えていたのはテストの方だけだった。

5 本の harness スクリプト、定数を持つ 1 個のモジュール、`harness/PROVENANCE.md` に記録されたコマンド、契約文書中の 1 文、そして Kubernetes のマニフェスト内のハードコードされた 3 つのフィールドが、いずれも private なクラスタの実際の context 名と namespace を運んでいた。誰かのクラスタを名指しするデフォルト値は便利さではなく、踏み台である。`--help` の出力をそのままコピーしたり、マニフェストを編集せずに適用したりすると、黙って別の誰かの環境を対象にしてしまう。これらのスクリプトは今、`TIERBOOK_K8S_CONTEXT` と `TIERBOOK_K8S_NAMESPACE` を読み、どちらも設定されていなければフラグと環境変数の両方を名指しして拒否する。

## 動いていることを見る方法

```console
tierbook validate --config candidates.json

tierbook compile --config candidates.json --out policy.json --max-age-days 90

tierbook observe --candidate box --metrics-url http://vllm:8000/metrics \
    --model-name <served-model> --authorised true --measured-on 2026-09-08 --out obs.json

tierbook assign --policy policy.json --request-id r1 --candidate box \
    --metrics-url http://vllm:8000/metrics --model-name <served-model> \
    --authorised true --previous obs.json --bound-kind lcb95 \
    --bounds '{"box":0.90,"api":0.70}' --costs '{"box":0.004,"api":0.012}' --log decisions.jsonl

tierbook accept --log decisions.jsonl --policy policy.json --uncertified-tolerance 0.10
```

`accept --policy` は floor と evidence-age の上限をアーティファクトから読み、二度目に打ち込まれた数値を信用することはない。何をどこから読んだかも記録する。実際のエンジンに対する phase 5 の走行の成果物は `docs/verify/` にあり、上で述べた 2 つのギャップも、不在から推測させるのではなくそこに名指しして記録されている。

## レビューする側への注記

特に第二の意見が欲しい箇所を 4 つ挙げる。

1. **expiry override を通って到達したアームは、サーブされるが uncertified として記録される。** その bound は floor をクリアしているが、その bound を支える evidence は family の freshness の上限を満たしていない。本リリースはこれを SCOPE 2 節の 4 条件を厳密に読む方向で解決している——サーブはするが certify はしない——「bound が floor をクリアした」ことそれ自体で十分だとは扱わない。これが実際には十分に支持されているアームを過小評価しているのか、それとも 2 節が要求する慎重さそのものなのかは検討の余地がある。
2. **floor は今、運用側の config やデプロイ時のフラグではなく、バージョン管理された ledger ファイルの中に住んでいる。** SCOPE は floor をファイルの一行と呼んでおり amendment 2 はそれを文字どおりに実装しているが、floor はレビューサイクルより速く変えたいとオペレータが望みうる、運用的な性格を持つ数値でもある。この数値の周りにある計測結果に比べて、より運用的なこの数値の置き場所として ledger が正しいのかは検討の余地がある。
3. **`floor_compliance` は 2 つのレートを持ち、悪い方を報告する 1 個の基準のままである。** これは SCOPE 12 節の 9 個という基準の数を 10 個に増やさないためである。これは統治文書の数を保つが、同時に caller は `numbers` の中を読まない限り、「certified トラフィックは pass した」と「すべての served トラフィックは pass した」を、それぞれ別に行動できる 2 つの結果として得ることができない。この圧縮が、それによって保たれる数よりも高い代償を払っているかどうかは検討の余地がある。
4. **C13 は部分的な対処で埋め合わせるのではなく見送られている。** アーティファクトは今も caller の `bounds` 引数が何かと食い違っているかどうかを答えられず、`no_false_certification` は本リリースでも捏造された bound をそのまま通す。今、小さな stopgap(警告や、未検証の bounds を示すフラグ)を出す代わりに、修正全体を次のリリースの最初の phase まで見送るという判断は、既に長くなっていたリリースの圧力の下で下された判断であり、強制された結論ではない。何らかの中間的な信号がそれでも本リリースに含まれるべきだったのかは、問うに値する。
