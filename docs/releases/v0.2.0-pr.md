# v0.2.0 — the log survives its own evolution, and exploration is specified and drawn from

| | |
|---|---|
| What this adds | A decision log that can grow a field without breaking every reader that predates it, one recorded home for the parameters a policy was compiled under, a per-family declaration of what labels a request and how long to wait for one, and exploration: an eligible set, a draw, and a recorded propensity that a family can only turn on once it has declared a labeller |
| What it does not add | Anything that closes the loop. `Log.attach_outcome` still exists and nothing calls it; a family can now declare a labeller without ever calling one. Anytime-valid bounds, change-point detection, and a value for the reserved candidate's scarce capacity are still absent, and C13 — the certified bound coming from the artifact rather than from whatever a caller types — is deferred, with the reason below |
| Verified | Against a live vLLM engine on a `g5.xlarge`, not a fixture: `observe` under a 20-way load, exploration configured at a 0.05 rate, `accept` reading a compiled policy's own floor and evidence-age limit. Separately, each of seven defects was reproduced at the commit before its fix and confirmed absent at `HEAD` |
| Tests | 1,077 passing, 3 skipped in `tests/`, and 302 passing in `harness/tests`, identically on Python 3.9.6 and 3.11.15 — checked directly on both, after a defect in the suite itself made that not true earlier in this release |
| Acceptance | 3 of SCOPE section 12's 9 criteria evaluated against the real-engine run: 2 passing, 1 failing, 6 `unsupported`. The failure is `default_is_not_a_hiding_place`, reported rather than tuned away — the example ledger's compiled policy is `certified: false` with no rules on a 20-item cohort, so every assignment goes to the default |

## Why

CONTRACT.md states the release as one sentence: make the log survive its own evolution, then explore safely into it, in that order. v0.1.0 made one turn of the loop run, but the record it wrote could not survive its own schema changing — adding a field to `Decision` made every older reader raise on every line, outside `Log.read`'s own corrupt-line tolerance, so a schema change killed a whole acceptance run instead of being counted by it. And nothing routed traffic anywhere except the deterministic candidate: v0.1.0's own release notes named "logged selection probabilities that vary" and "exploration or shadow allocation" as the load-bearing gap, because every decision a deterministic policy makes has propensity 1, under which the counterfactual arm has no data and an off-policy estimate is unidentified. This release closes the first gap because the second cannot be built on top of an artifact that cannot change shape underneath it, and only then turns exploration on.

## What changed

**The log survives a field being added.** `record.from_row` replaces `accept._as_decision`'s `Decision(**kw)` splat. A row's unknown key is ignored and named rather than dropped; a row whose `schema_version` exceeds what the reader knows is refused by name rather than parsed optimistically; a row missing a field its own version requires raises `Incomplete` naming it. A row with no version at all is read as version 1, by the reader's own code rather than by a convention enforced by nobody. The same treatment reaches a candidate row's unknown keys, by position, once the audit found `bound_n`/`bound_attempted` is itself a candidate-level field a future entry may replace, and the original design had only ever named the decision row. Two structural gaps closed alongside the reader itself: the closed vocabulary `EXCLUSION_REASONS` was checked only against itself, so deleting each of its nine values in turn and running the whole suite found four — `not_authorised`, `latency_infeasible`, `unavailable`, `no_bound` — that the suite never exercised at all, meaning `record.admissible` and `serve._why_not` could return a string `Candidate.__post_init__` would refuse, and the refusal would land at write time in production on a path no test covers; the fix tests the producers against the vocabulary instead of testing the vocabulary against a second list of itself. And the ignored-key list `from_row` returns reached nobody: `Log.read` and all three of `accept`'s call sites discarded it, so an operator rolling a reader back onto a log a newer mechanism wrote would see every line read fine and every criterion compute, with the fields the newer mechanism recorded — a propensity, an eligible set — silently absent from what the criteria saw and no signal that the reader was behind its own log. `Log.read` now carries `__ignored_keys__` by name, and `accept`'s report records it.

**One home for the parameters a policy was compiled under.** Before this release the compiled artifact carried `certified: true` and not the floor it was certified against: the floor had three supply points — the CLI `assign` verb, `serve.route_once`, `accept` — and zero recorded copies, so no criterion computed over a log could be known to have used the policy's own floor. The audit that went looking for where the floor entered the compile path so it could be carried through found that it entered nowhere: `grep floor` over the config and schema files returns nothing, and the objective's own constraints carry only a relative non-inferiority margin. The floor was never declared anywhere in this repository, so there was no first copy to record. It is now a per-family declaration — `families` stops mapping a name to a bare reference-candidate string and becomes an object carrying `reference` and `floor`, `config_format` moves from 1 to 2, and a bare string is refused naming what to change — because SCOPE calls the floor a row in a reviewable, version-controlled file, and it is per family, which a single `compile --floor` flag (built, and withdrawn before shipping) cannot be: two families with different accuracy requirements would silently share whichever number was typed. `decide.Policy.parameters` now carries the floor, `max_evidence_age_days` and `staleness_limit_days`, and `decide.parameter(policy, name, supplied=None)` is the single reader: nothing supplied returns the artifact's value, a supplied value equal to the artifact's is accepted, a different one raises naming both rather than preferring either, and a name the artifact never recorded raises when a value is supplied for it. `assign --floor` and `accept --floor` are now optional; a mismatch against the artifact exits 4; `accept` gains `--policy`, and given neither `--policy` nor `--floor` it exits 2 — argparse's own code for a required argument nobody supplied, kept apart from 4 because the two failures call for different operator actions. The freshness limit the falsifier checks against got the same treatment for the same reason: `accept`'s report now carries `max_age_days` and its own provenance line, because a run made with no `--policy` checks three of admissibility's four conditions and the report was not honest about which three.

**A family declares who labels it, and no labeller means no exploration rate.** `Log.attach_outcome` exists and nothing calls it, and exploration on top of that produces randomised assignments nobody can learn from, so the join is a prerequisite rather than a companion. Each family now declares `label_source`, `max_label_latency_s` and `label_independent_of_candidate` in the same per-family object the floor lives in. `label_source` is drawn from the tier record's own `oracle.kind` enum, extended by exactly one value, `none` — read from the schema file rather than copied, so a second, coarser vocabulary for the same concept cannot drift from the first, which an earlier draft of this entry would have created by declaring the field on the measurement schema instead of the config a future request is judged against. `label_independent_of_candidate` exists because a judge that is also a candidate in its own family scores that candidate perfectly by construction, a gate the tier record already enforces offline and the online declaration would otherwise silently drop. `exploration_rate` may appear on a family only when `label_source != "none"` and `label_independent_of_candidate` is true; otherwise `load_config` refuses, naming both the rate and the reason. The refusal is a load failure, not a runtime discovery — the artifact cannot represent the missing combination at all, rather than representing it and hoping something notices at runtime. `record.classify_label(decided_at, now, max_label_latency_s, label)` turns those declarations into `labelled` / `pending` / `missing`, and `Log.read` never reclassifies a row below `schema_version` 2: an old outcome keeps the label state it was written with rather than being silently restated under a latency rule it was never governed by.

**Exploration: an eligible set, a draw, a recorded propensity, and where certification actually comes from.** `explore.clears_floor` is separate from `admissible` because `admissible` decides expiry before comparing the bound, and reusing it could not reach the arm a freshness ratchet had locked out — the one door exploration needs, because an arm never chosen is never labelled. Every other exclusion still applies: a candidate that is `not_authorised`, `latency_infeasible`, `unavailable`, `not_priced` or has `no_bound` is not explored into, because routing paid traffic through a randomiser whose eligible set cannot be enumerated is the wrong refusal to skip. One draw happens per decision, and the recorded propensity is the conditional probability of the arm actually chosen under the draw actually performed — at a 0.05 rate over one alternative that is 0.95 for the incumbent and 0.05 for the alternative, not the 0.95/0.025 an earlier draft's own example got wrong. Reaching this mechanism surfaced a defect in SCOPE itself before the mechanism could ship correctly: `explore.clears_floor` can return eligible on evidence that is stale by the family's own limit — that is the override's whole purpose — while `record.admissible`'s fourth condition, freshness, independently returns `evidence_expired` on the same candidate, and the falsifier reported the resulting assignment `certified` for exactly the case exploration exists to create. SCOPE section 2 named three admissibility conditions while the code had enforced four since v0.1.0; the document is corrected to name the fourth, and `serve.route_once` now derives `certified` from full admissibility, freshness included, on every assignment, explored or not. The arm reached through the override is still served — the label still comes back, the evidence still refreshes, which is the whole point of opening the door — it is simply not certified while the evidence behind its bound is stale. `floor_compliance` stays one criterion, matching SCOPE section 12's count of nine, but reports two rates in its `numbers` — `certified` and `all_served`, each with its own bound and sub-verdict — and takes the worse of the two as its own verdict, so a pass on one half while the other fails cannot present as a pass.

**The rate criteria refuse to pool across a schema-version mixture.** Six numbers move silently at a version boundary once exploration exists: the exploration share dilutes by log length rather than behaviour, a default's propensity-1 rows contribute infinite-weight certainty to a weighted estimate, and more. `accept.check_all` gains `pool_across_versions: bool = False`; with a log spanning more than one `schema_version` and pooling not requested, `floor_compliance`, `default_is_not_a_hiding_place`, `exploration_cost` and `spend_regret` return `UNSUPPORTED` naming the versions present and the count in each, while `no_false_certification` computes regardless because it is a per-decision universal claim rather than a rate a mixture can distort. The guard is applied after each criterion computes, not before, so it overwrites only a `PASS` or a `FAIL` and never replaces a criterion's own, more specific `UNSUPPORTED` — a stub criterion's "I have no implementation" is a different operator action from "your log mixes two versions," and applying the guard first was found to be silently substituting the second for the first.

**Upgrading a real ledger now takes two loads, not six.** `load_config` used to raise on the first family problem it met and stop; measured against this project's own shipped v0.1.0 candidate file, that is five sequential, individually correct refusals — one problem discovered per load. It now collects every problem across every family into one `ConfigError` and raises once, and the round-trip count is asserted directly against the real file rather than just the aggregation, so a message that lists two of five problems cannot pass the test that a message lists all of them.

## Two breaking changes, and their measured migration cost

**`config_format` moves from 1 to 2.** `families` stops mapping a name to a bare reference-candidate string and becomes an object carrying `reference`, `floor`, and (appended by the labeller and exploration entries above, without a second version bump) `label_source`, `max_label_latency_s`, `label_independent_of_candidate` and `staleness_limit_days`. A format older than the current one is fully validated — both shapes are known, and the difference between them is exactly what an operator needs told — while a format newer than the current one is refused on the version alone, before any family is inspected, because a shape the reader does not know cannot be meaningfully checked against the shape it does. Measured against this project's own v0.1.0 candidate file, before the load-collection fix above the migration took six loads: the version, then the first family's shape, then that family's four missing keys, then the second family, one problem discovered per load. After it, two: one message naming every problem across every family, then a clean load. A message that names a shape now names the whole shape rather than the two keys it started with — an operator who fixed exactly `{"reference": ..., "floor": ...}` on the strength of an earlier message got a second refusal naming the four keys nobody had told them about, which by itself accounted for four of the original six round trips.

**The decision record's `schema_version` moves from 1 to 2.** This direction takes no migration at all. A line with no `schema_version` is read as version 1, silently and without error, and `record.from_row` reads this project's own v0.1.0 decision log with nothing raised and nothing lost: every field a v0.1.0 line carries is a field the version-1 shape knows. The two breaking changes are handled oppositely on purpose. The config format is validated in full because both shapes are known documents an operator edits and needs told about completely; a decision log's older rows are read as exactly what they always were, because nothing about a past decision changes by being read with a newer tool.

## What this release found in itself

### The artifact shipped a list claiming three things were missing that had already shipped

`decide.MISSING_FOR_A_CLOSED_LOOP` is a six-item tuple written into every compiled policy artifact as `missing_for_a_closed_loop`, "so their absence is not mistaken for presence." At this release's own `HEAD`, three of the six were false: a state collector, false for a whole release — it shipped in v0.1.0 as `observe.py`, and v0.1.0's own release text said the tuple "closes the first" and then never removed the entry — and logged selection probabilities that vary, and exploration itself, both false the moment this release's own exploration mechanism shipped, with `Decision.selection_probability` varying and `explore.py` existing. `tests/test_decide.py::test_the_artifact_names_what_a_closed_loop_still_needs` required the shipped artifact to keep claiming exploration and varying propensities were absent, and it passed through every prior entry in this release because none of their diffs touched the tuple. The guard that let this through asserted that four substrings were present in the tuple's text; adding a mechanism cannot fail a check that only looks for the mechanism's absence to be *claimed*, which made the fabrication as invisible by construction as the enum-membership defects above. The three shipped items are removed, and every remaining claim — anytime-valid bounds, change-point detection, a value for the reserved candidate's scarce capacity — is now tied to a probe, a callable naming the symbol or module whose existence would falsify it, with a test asserting every claim and its probe agree. A claim whose probe cannot be written is a claim too vague to ship in a machine-readable artifact.

### Exploration recorded that the randomiser ran, not that traffic was diverted

`explore.draw` returned the reason `"explored"` for both outcomes of an active draw — the alternative winning, and the incumbent winning anyway — and `serve.route_once` set the `exploration` field straight off that string. Measured over 5,000 seeds at a declared rate of 0.05: the reason read `explored` on 100.0% of draws while only 5.52% of draws actually diverted to the alternative. `accept.exploration_cost` computed its share directly from that field, so it reported the exploration share as 100% against a 25% budget for a mechanism that was, in fact, 5.52% inside it — a criterion failing a mechanism operating well within its own budget, which pressures an operator to shrink or disable the exploration the freshness-ratchet fix above depends on for recovery. The reason the field could not carry the distinction is that its vocabulary was one value short: `exploration_reason` already distinguished no mechanism, an empty eligible set and a zero rate as three separate causes sharing one bit, and gained a fourth, `not_diverted`, for the randomiser running and the incumbent winning anyway. `exploration` is now derived as `chosen != deterministic` — the signal `route_once` already computed three lines away — and the propensity is unchanged: an incumbent that wins under an active draw still has propensity `1 - rate`, not 1, because the propensity and the diversion flag answer different questions, one for off-policy identification and one for budget accounting, and conflating them is what produced this defect.

### The rate criteria excluded exactly the rows this release taught them to distinguish

`accept._unreadable` read `outcomes["__bad_lines__"]` only, and never the `__unreadable_rows__` counter this same release's reader added for a row that parses as JSON but fails `from_row` — a version the reader does not know, a field the row is missing. Reproduced with 40 labelled successes and 15 rows stamped an unreadable `schema_version`, all of which would have been labelled failures: `floor_compliance` reported `pass`, rate 1.0, lower bound 0.9278, while the true rate counting the dropped rows is 0.7273, which fails an 80% floor. This is the same shape as the criterion's own denominator split between certified and all-served traffic, applied to a category this release itself introduced and never extended the same guard to. Both classes of unreadable row are now counted and named separately in every rate criterion's population, and `default_is_not_a_hiding_place` gains the `outcomes` parameter it did not take at all before — which is why it had no guard against either class.

### A bound function accepted more successes than trials, and answered confidently

`accept.clopper_pearson_lower(n, k, alpha)` computes the lower confidence bound every floor comparison in this project rests on. Its boundary case, `if k >= n: return alpha ** (1.0 / n)`, is correct at `k == n` and was applied to `k > n` as well — a contradiction, not a boundary — so twenty successes recorded against sixteen trials returns `0.8293`, accepted. The error is high, which means it flatters the candidate rather than refusing: found while investigating C13 below, by reading the example ledger's `self-hosted-a` tier as clearing an 0.80 floor at `0.8293` with the arguments transposed, when the tier's true bound is `0.4922`. `k > n` now raises, naming both numbers; `n <= 0`, which previously reached `alpha ** (1.0 / 0)` and crashed with an unlabelled `ZeroDivisionError`, now raises a stated error instead.

## What phase 5 established, and what it did not

Phase 5 stood up one `g5.xlarge` running vLLM 0.29.0 against `Qwen/Qwen2.5-0.5B-Instruct` under a 20-way concurrent load, and destroyed it after. Established: `observe` reads occupancy rather than returning a constant — over 400 samples, `inflight` took 19 distinct values from 2 to 20, which one reading could not have shown, since a constant is indistinguishable from a measurement until it moves. Asked for a model the engine is not serving, `observe` reports the variable absent with the metric and label set that were missing rather than defaulting to a zero that would read as an idle engine. The documented path runs in order — `validate`, `compile`, `observe`, `observe --previous` for a rate — and `accept --policy` records the floor (0.8) and the evidence-age limit (90) it checked against, each with a provenance line naming the artifact, with `ignored_keys` empty because this run's reader understood every field it saw. The label recorded is "the engine returned a non-empty completion," not task success, and the report says so rather than attaching a success signal nobody measured. Separately, each of seven contract entries — C5, C6, C8, C9, C10, C11, C12 — was reproduced at the commit before its fix and reconfirmed absent at `HEAD`, which is the basis for the "Verified" row above.

Not established: exploration's live behaviour. Over 400 live decisions the draw returned `no_eligible_arm` every time, against a declared rate of 0.05, and the diverted share was 0. `serve.candidate_set` builds the eligible set from the policy's own rules and its default, and the policy compiled from the example ledger has no rules at all — the compiler refused to certify anything for that family on a 20-item cohort — so the eligible set has exactly one member and the draw correctly declines on every call. That is correct behaviour on this fixture and it is not evidence about the draw itself; whether a policy with no certified rules should ever have let exploration reach further than its own rule set is a design question this run does not answer, since routing paid traffic into a candidate a held-out fold refused is exactly what the compiler's refusal exists to prevent. The draw's arithmetic is verified separately and hermetically, over 5,000 seeds at rate 0.05, where it reproduces the 5.52% figure used above. And C13 is not fixed: a caller can still assert a bound the evidence does not support, and `no_false_certification` will pass it, because the falsifier computes admissibility from the caller's own number rather than from anything the artifact recorded.

## C13 is deferred, and this is the reason

C13 asked that the bound `route_once` compares against the floor come from the artifact rather than from whatever a caller passes, by the same rule amendment 2 established for the floor itself. Implementing it surfaced that the artifact does not carry the quantity to give: `policy.assign_family`'s `ranked` carries `quality_lcb`, a paired lower bound on the *difference* against a reference tier — `-0.469` for the example ledger's `self-hosted-a` — and SCOPE section 2 clause 1 asks for an absolute lower bound on success, which the compiler has never computed. Deriving it is possible with the exact bound function already in this package, applied to each tier's own `solved`/`attempted` pair, and doing so changes what a compiled policy claims rather than merely where a number is read from: on the example ledger at a 0.80 floor, only the reference tier clears it (`api-cheap-a` 16/20 → 0.5990, `api-strong-a` 20/20 → 0.8609, `self-hosted-a` 14/20 → 0.4922) — on a 20-item cohort this project's own README already calls too small to trust. Absorbing that change at the end of a release that had already taken thirteen entries would mean redesigning what a compiled policy asserts alongside everything else in flight, with the example ledger's own answer changing as a side effect — which is how a release acquires a defect nobody reviewed rather than how it fixes one. C13 goes to the next release's first phase with this observation as its input. Stated plainly rather than left implicit: a caller can assert a bound the evidence does not support, and the falsifier will pass it, because it computes admissibility from the caller's own number.

## Also in this release

Four tests in `harness/tests` seeded a stall timer with a literal `0.0` and compared it against `time.perf_counter()`, whose reference epoch the language leaves undefined — on the machine this was found on it is process start under Python 3.9 and boot time under Python 3.11, an 803,137-second difference that tripped a 2,400-second stall ceiling before a single line was parsed. The four tests passed on 3.9 and failed on 3.11 off the same commit; the production path was already correct, since it takes both readings from `perf_counter()` itself, and only the test supplied a value from no clock at all.

Five harness scripts, a module of constants, a recorded command in `harness/PROVENANCE.md`, a sentence in a contract document, and three hardcoded fields in a Kubernetes manifest all carried a real context name and namespace from a private cluster. A default that names someone's cluster is not a convenience, it is a footgun — copying the `--help` output, or applying the manifest unedited, would silently target somebody else's environment instead of failing loudly. The scripts now read `TIERBOOK_K8S_CONTEXT` and `TIERBOOK_K8S_NAMESPACE` and refuse, naming both the flag and the variable, when neither is set.

## How to see it work

```console
tierbook validate --config candidates.json

tierbook compile --config candidates.json --out policy.json --max-age-days 90

tierbook observe --candidate box --metrics-url http://vllm:8000/metrics \
    --model-name <served-model> --authorised true --measured-on 2026-09-08 --out obs.json

tierbook assign --policy policy.json --request-id r1 --candidate box \
    --metrics-url http://vllm:8000/metrics --model-name <served-model> \
    --authorised true --previous obs.json --bound-kind lcb95 \
    --bounds '{"box":0.90,"api":0.70}' --costs '{"box":0.004,"api":0.012}' --log decisions.jsonl

tierbook accept --log decisions.jsonl --policy policy.json --uncertified-tolerance 0.10
```

`accept --policy` reads the floor and the evidence-age limit from the artifact rather than trusting a second typed number, and records which it did. Artifacts from the phase-5 run against a live engine are in `docs/verify/`, including the two gaps named above rather than left to be inferred from what is absent.

## Review notes for a reader

Four places most worth a second opinion:

1. **An arm reached through the expiry override is served but recorded uncertified.** Its bound clears the floor; the evidence behind that bound does not meet the family's freshness limit. This release resolves that in favour of the strict reading of SCOPE section 2's four conditions — served, not certified — rather than treating "the bound cleared the floor" as enough on its own. Worth checking whether that undersells a genuinely well-supported arm, or is exactly the caution section 2 requires.
2. **The floor now lives in a version-controlled ledger file rather than an operational config or a deploy-time flag.** SCOPE calls it a row in a file and amendment 2 follows that literally, but a floor is also the kind of number an operator may want to change faster than a review cycle allows. Worth checking whether the ledger is the right place for a number that is more operational than the measurements around it.
3. **`floor_compliance` stays one criterion carrying two rates and reporting the worse of them**, so as not to grow SCOPE section 12's nine criteria to ten. That keeps the governing document's count intact and it also means a caller cannot get "certified traffic passed" and "all served traffic passed" as two separately actionable outcomes without reading into `numbers`. Worth checking whether the compression costs more than the count it preserves.
4. **C13 is deferred rather than patched with something partial.** The artifact still cannot answer whether a caller's `bounds` argument disagrees with anything, so `no_false_certification` still passes a fabricated bound this release. Deferring the whole fix to the next release's first phase, rather than shipping a smaller stopgap (a warning, an unchecked-bounds flag) now, is a judgement call made under the pressure of an already-long release rather than a forced one, and it is worth asking whether some intermediate signal belonged in this release regardless.
