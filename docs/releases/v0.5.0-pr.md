# v0.5.0 — the certification plane: graded outcomes in, a held-out-checked assignment out, handed to the router

| | |
|---|---|
| What this adds | Four verbs (`ingest`, `derive`, `drift`, `export-policy`) that turn graded observations into a per-task-type assignment that is the cheapest per accepted task, check it on held-out items, export it to vLLM Semantic Router, and read the router's traffic back; an example that runs the loop; two gateway patches the loop needs |
| What it does not add | A request-path selector, a learned router, an online bandit, a self-hosted arm priced inside the plane. The ledger, compile and route path of v0.1-v0.4 is unchanged |
| Verified | The loop on billed traffic through vllm-sr 0.4.0 in Docker, across three deployments: 9,480 calls over seven arms, about $14.54 at the gateway's rates ([record](https://github.com/littlemex/tierbook/blob/f7a72b95d0f9392477b62359c199903c4fae9734/docs/verify/v0.5.0-certification-loop.md)) |
| Tests | 2,256 passing and 3 skipped on Python 3.14; 2,259 passing on Python 3.10 from a fresh clone of this branch. 33 tests for the plane, written apart from the code against the design document, 12 of them regressions for review findings |

## Background

Between the first design and now, per-request routing became a crowded and capable layer. vLLM Semantic Router 0.4.0 ships a declarative signal, decision and algorithm pipeline with a dozen selection algorithms, a cost-and-quality `multi_factor` selector, a replay log and a versioned configuration contract; LiteLLM, Kong, Cloudflare, OpenRouter, Azure and Bedrock all route per request with some notion of cost ([survey](https://github.com/littlemex/tierbook/blob/f7a72b95d0f9392477b62359c199903c4fae9734/docs/prior-art-2026-11.md)).

What none of them does is derive an assignment from the operator's own graded outcomes and say how sure it is. Prices are hand-written cards, quality comes from public indexes or opaque classifiers, and learning is process-local, manual, or closed. vllm-sr's own `success_constrained` proposal (2026-09-04, unimplemented) describes the missing object: among candidates whose calibrated success probability meets a target, the cheapest. The literature says where the value in that object is: most routing gain is a static per-task-type assignment (arXiv:2608.23023), the unit that survives price changes is cost per solved task (arXiv:2504.13359), and a choice reported on the data it was made on is optimistic (arXiv:2510.18161, arXiv:2608.08265).

## Approach

**tierbook stops being a router and becomes the plane beside one.** It computes, from observations, which arm each task type should go to, at what spend per accepted task, with what guarantee, and writes it as configuration the request-path router already understands. The design is [`docs/DESIGN-v0.5-certification-plane.md`](https://github.com/littlemex/tierbook/blob/f7a72b95d0f9392477b62359c199903c4fae9734/docs/DESIGN-v0.5-certification-plane.md).

| decision | compared with | pros | cons | why this |
|---|---|---|---|---|
| a certification plane that exports to the router | another request-path selector | does what no router does; reuses the router's classification, observability and deployment | depends on the router's configuration contract, which moves | the selector is a commodity; the certified assignment is not |
| the unit is the per-task-type assignment | per-request prediction | the measured gain is there; a router can execute it as a lookup | leaves the within-type residual on the table | three independent studies and this project's own measurements found per-request learning does not beat it |
| cost per accepted task, recomputed from today's prices | billed amounts at observation time | a price change alone re-derives the policy; nothing is re-measured | depends on an accurate rate card | prices move faster than measurements should be repeated; the gateway patch makes the card readable rather than typed |
| choose on one half of the items, check on the other | a corrected bound on all items | valid whatever the search did; simple to read | halves the sample for each step | the failure it prevents was measured here (a 6.7-point gap) and is the subject of the literature cited |
| everything that decides certification is declared, with no defaults | sensible defaults | a different study can express a different conclusion; nothing is chosen for the operator | a longer declarations file | the project's governing constraint: logic is injected, never built in |

What each verb owns is one sentence, and the design keeps them apart: `ingest` maps and joins and never grades; `derive` bounds, compares and states the status (`certified`, `unconfirmed`, `contradicted`, `unassignable`) and the fallback; `export-policy` translates or refuses; `drift` reports the diff against a re-derivation, contradiction checks on fresh traffic, cells that need measuring, and attempts that reached no arm. There is no `loop` verb; the loop is their composition, and `examples/certification_loop/` is one.

`predict.py` and `describe.py` are removed: no importer, no test, and an install extra that did not exist.

## Evidence

All on 2026-11-08, with the commands in [`examples/certification_loop/README.md`](https://github.com/littlemex/tierbook/blob/f7a72b95d0f9392477b62359c199903c4fae9734/examples/certification_loop/README.md), MMLU-Pro biology, history, math and law, seven arms through an OpenAI-compatible gateway.

| step | what was run | what came out |
|---|---|---|
| derive v1 | `tierbook derive` on 1,000 items x 5 arms | three task types to `claude-sonnet-5`, history to `qwen3-next-80b`, all `certified`; 0.84 of the single best arm's spend per accepted task on 489 common held-out items |
| route v1 | `vllm-sr serve` with the exported config, 160 routed requests | every request sent to a Claude arm returned 502; the router log names `unknown field "cache_read_input_tokens"`; `drift` reports 135 unattributed attempts |
| derive v2 | arms the router can reach, plus two arms `drift` listed as never observed | all four task types to `gpt-6.1-terra` (the single best arm, ratio 1.00) |
| route v2 | redeploy, 160 new requests | 159 succeeded, all on `gpt-6.1-terra`; `drift`: four `confirmed` |
| price only | `gpt-6.1-terra` rates tripled in the candidate file, nothing re-measured | `drift` reports three task types moving to `gpt-5.6-terra`; v3 spends 0.79 of the single best arm on 508 common held-out items |
| route v3 | redeploy, 160 new requests | biology, history and law reached `gpt-5.6-terra`, math `gpt-6.1-terra`; `drift`: two `confirmed`, two `consistent` |

The run changed code, and each change is listed in the record with what found it: the exporter's provider shape (`defaults.model`, backend `provider`) for vllm-sr 0.4.0; the listener address, which had published the router on every host interface and now defaults to loopback; `finish_reason` and cut-off counts after a 32-token budget turned reasoning into wrong answers; unattributed attempts after a window of 502s read as an empty one; ingest and drive replacing rather than appending.

The gateway changes are patches, not edits to the gateway: [`infra/patches/stratoclave/`](https://github.com/littlemex/tierbook/tree/f7a72b95d0f9392477b62359c199903c4fae9734/infra/patches/stratoclave). 0001 lets a caller read its billing rates and per-request cost; 0002 makes Claude responses on the OpenAI-compatible surface carry canonical cache usage. `GATEWAY_REF` moves to the commit they apply to. Nothing is needed in distributed-ai.

What the record does not show is stated in it: the guarantee is per task type and conditional on the dataset's labels, and the router classified 130 of 159 and 125 of 158 routed requests into their own task type; the held-out halves were checked twice under one split; the v3 price is a probe; Claude arms were measured but not routed.

## Test plan

Needs Python 3.10+, Docker, an OpenAI-compatible gateway serving the arms in `examples/certification_loop/candidates.json`, and its key. Paste as one block; it measures a small sample (about 840 calls), routes 40 requests through vllm-sr on loopback, and removes what it started.

```bash
export GATEWAY_URL=https://your-gateway.example/v1
export TIERBOOK_API_KEY=sk-your-key
export WORK=$HOME/tierbook-v050-test
rm -rf "$WORK" && mkdir -p "$WORK" && cd "$WORK"
git clone -q --branch epic/v0.5-certification-plane https://github.com/littlemex/tierbook.git
python3 -m venv venv && venv/bin/pip -q install ./tierbook pytest pyarrow 'vllm-sr==0.4.0'
(cd tierbook && ../venv/bin/python -m pytest -q)
EX=$WORK/tierbook/examples/certification_loop
curl -sL -o mmlu.parquet https://huggingface.co/datasets/TIGER-Lab/MMLU-Pro/resolve/main/data/test-00000-of-00001.parquet
venv/bin/python -I $EX/prepare_mmlu_pro.py --parquet mmlu.parquet --categories biology,history,math,law --per-category 30 --seed 1 --out items.jsonl
venv/bin/python -I $EX/prepare_mmlu_pro.py --parquet mmlu.parquet --categories biology,history,math,law --per-category 10 --seed 1 --skip 30 --out routed-items.jsonl
venv/bin/python -I $EX/drive.py direct --items items.jsonl --candidates $EX/candidates.json --base-url "$GATEWAY_URL" --out calls.jsonl --run m1 --max-tokens 1024
venv/bin/python -I $EX/grade.py --calls calls.jsonl --items items.jsonl --out outcomes.jsonl
venv/bin/tierbook ingest --calls calls.jsonl --outcomes outcomes.jsonl --out obs.jsonl
venv/bin/tierbook derive --observations obs.jsonl --candidates $EX/candidates.json --declarations $EX/declarations.json --out policy.json
venv/bin/python -c "import json,os,sys; c=json.load(open(sys.argv[1])); [v['endpoint'].update(base_url=os.environ['GATEWAY_URL']) for v in c['candidates'].values()]; json.dump(c, open('candidates-live.json','w'), indent=2)" $EX/candidates.json
venv/bin/tierbook export-policy --policy policy.json --target vsr --candidates candidates-live.json --out vsr.yaml --allow-unconfirmed --signal biology=biology --signal history=history --signal math=math --signal law=law --signal-categories biology=biology --signal-categories history=history --signal-categories math=math --signal-categories law=law --management-bind 0.0.0.0 --management-port 18080
venv/bin/vllm-sr config validate --config vsr.yaml
venv/bin/vllm-sr serve --config vsr.yaml --minimal --replace-active-config
venv/bin/python -I $EX/drive.py routed --items routed-items.jsonl --router http://127.0.0.1:8801/v1 --model tierbook/routed --out routed.jsonl --run routed-1 --max-tokens 1024
venv/bin/python -I $EX/grade.py --calls routed.jsonl --items routed-items.jsonl --out routed-outcomes.jsonl
venv/bin/tierbook ingest --calls routed.jsonl --outcomes routed-outcomes.jsonl --out routed-obs.jsonl
venv/bin/tierbook drift --observations obs.jsonl --fresh routed-obs.jsonl --deployed policy.json --candidates $EX/candidates.json --declarations $EX/declarations.json --out drift.json
venv/bin/vllm-sr stop
cd "$HOME" && docker run --rm -v "$WORK:/w" busybox sh -c 'rm -rf /w/* /w/.[!.]*' && rm -rf "$WORK"
```

What to look for: the suite ends `passed` with no failures; `derive` prints one line per task type with a status and a reason (with about 15 held-out items per task type, some task types are `unassignable` or `unconfirmed`, and the export carries `unconfirmed` ones only because of `--allow-unconfirmed`); `vllm-sr config validate` prints `Configuration is valid` and `serve` prints `vLLM Semantic Router is running`; `drift` prints a `check` line per certified task type, `undetermined` because 10 routed items per task type is below the declared `min_items` of 20, and `changed` lines where the routed window moved a re-derivation. The router's model files are written by its containers as root, which is why cleanup removes them through a container. This block was run as written on 2026-11-08 against this branch; there, two task types were `certified` on `gpt-6.1-terra`, the router started, all 40 routed requests returned, and cleanup left nothing behind.
