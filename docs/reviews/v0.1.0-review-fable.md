## Q1. Is the refusal complete? No. Enumerated paths for wrong-but-plausible values into `decide`:

1. **`model_name=None` silently sums across every series.** `parse_metrics`'s own docstring says summing across `model_name` "would report another candidate's occupancy as this one's" — and then `_sum_metric` with `labels=None` does exactly that. A caller omitting `model_name` on a multi-model engine gets an inflated (or, for the counter, a merged) value recorded with full confidence. The safe behavior would be to refuse when multiple `model_name` values are present and no filter was given. This is the single largest hole, and it's the one the module's own comments identify.

2. **The NaN comment is false in the multi-series case.** "Dropped here, which makes the metric absent" — only if it was the *only* series. If a saturated engine exports three series and one is NaN, the other two are summed: a **partial sum**, not an absence. Same for any unparseable value (`continue` on `ValueError`) and for `+Inf`, which the regex `[-+0-9.eE]+` cannot match at all. Partial sums of `inflight` are precisely the "saturated engine reads as having room" failure this module claims to preclude.

3. **Label parsing is fragile in a way that produces partial sums, not refusals.** `labels.split(",")` breaks on any label value containing a comma; the regex `\{(?P<labels>[^}]*)\}` breaks on `}` in a value; escaped quotes aren't handled. A dropped series again yields a partial sum (see 2), which reaches `decide` as a plausible number.

4. **"Every reading carries its own `as_of`" is false.** `observe()` computes `now` **once, before the fetch**, and stamps every reading with it. Consequences: (a) `spread_s` is always `0.0` for any observation this function produces — the property advertised as the defense against "a state assembled minutes apart" is dead code; (b) the counter's timestamp is wrong by the fetch latency (up to the 5s timeout), which biases `arrival_rate_per_hour`, worst over short intervals; (c) every reading claims a freshness it doesn't have.

5. **`available: True` means "an HTTP body arrived," not "the engine is serving."** A reverse proxy returning a 200 error page, or the wrong service entirely, records `available:candidate = True` — a fresh, sourced, wrong observation. The failure branch is argued carefully; the success branch concludes availability from reachability, the exact inference the `gateway_authorised` docstring forbids for authorisation.

6. **`previous` is unvalidated.** No check that the previous counter reading came from the same URL, the same `model_name`, or within any maximum interval. Differencing counters from two different engines produces a huge plausible rate; differencing across hours produces a stale average presented as a current rate; a counter that reset and then *exceeded* its old value passes the `c1 < c0` check and understates the rate. All three reach `decide` as `arrival_rate_per_hour`.

7. **A future `measured_on` yields a negative `evidence_age_days`**, recorded without refusal, and trivially passes any freshness guard.

8. **No identity check ties `metrics_url` to `candidate`.** Point the collector at candidate A's endpoint with `candidate="B"` and you get perfectly qualified keys (`inflight:B`) carrying A's occupancy. Nothing in the module can detect this.

The refusal discipline is real for *absent* data. It is not complete for *wrong* data, and 1–3 are all in the "looks like a working collector" class the docstring says it exists to prevent.

## Q2. The section 9 field that cannot support its claim: `candidates[].excluded_because`

Its claim, per the docstrings: the candidate set with the reason each was excluded, so an exclusion analysis can be aggregated over the log; the closed vocabulary exists because "'other' in a log is a field nobody can aggregate."

`serve.candidate_set` **fabricates the reason at record time from what dictionaries the caller passed**, with no access to why `decide` actually excluded anything:

- not in `bounds` → `no_bound`; not in `costs` → `not_priced`; otherwise → **`below_floor`, asserted without ever comparing the bound to any floor** (the function doesn't know the floor).
- Four of the eight closed reasons — `not_authorised`, `latency_infeasible`, `unavailable`, `evidence_expired` — are **unreachable** from this code path. The log will show a clean, aggregable distribution over three reasons no matter what actually happened.

A closed vocabulary of invented values is worse than "other": it aggregates confidently into nonsense. The `__post_init__` validation guarantees membership in the enum, i.e., exactly the property that makes the fabrication invisible.

Runners-up, both real:

- **`state_ref` is a dangling pointer.** It's a content hash of the observation, but *nothing in this release persists the observation*. "The observation is logged separately by whoever collected it" — no code here does, so the reference identifies content nobody stored. The record looks like it identifies the decision's state and doesn't.
- **`bound_kind="lcb"` is asserted for any supplied bound.** If a caller passes point estimates as `bounds`, the log claims they were corrected lower bounds, and `no_false_certification` "passes" against them (see Q3/Q4).
- Minor but on-theme: `decided_at: float = field(default_factory=time.time)` directly contradicts the class docstring "none defaults to something plausible."

`selection_probability=1.0` is *not* the answer: it's a true value honestly recorded, and both `serve` and `accept` say what it can't support.

## Q3. The third verdict — mostly honest, but three passes are unearned and one statistic is asymmetric by construction

**`floor_compliance` passes on absence of evidence.** The test is: FAIL if `P(X ≤ k | p=floor) < 0.05`, PASS otherwise (n ≥ 30). This can only fail with strong evidence but passes with none. Concretely: n=30, floor=0.8, k=22 → realised rate 73.3%, *below the floor*, p ≈ 0.13 → **PASS**, with a detail sentence saying the rate "is not below the floor beyond sampling error." A rate below the floor should at most be `unsupported`; a PASS should require the compliance direction to be shown (e.g., a lower confidence bound on the realised rate clearing the floor, or rejecting `p ≤ floor − δ`). As written, the module commits the exact sin its docstring names: "reporting a pass it did not earn." Also: `n < 30` and `significance=0.05` are thresholds chosen *here* — the same move `default_is_not_a_hiding_place` refuses for tolerances ("grading our own work"). Were they pre-registered in SCOPE? Not checkable from what's here.

**`floor_compliance` drops unlabelled decisions and treats that as ignorable.** It counts `unlabelled_certified` but a PASS with, say, 30 labelled and 200 pending would still be PASS. If labelling is missing-not-at-random (failures less likely to get an oracle verdict — the usual case), the rate is inflated. The verdict should be `unsupported` above some missingness share, or at least the PASS detail should carry the caveat. Related: the module's own justification is backwards — "a missing label silently read as a failure moves a realised success rate in the direction that flatters the floor." Reading missing as failure *lowers* the rate, which is conservative. It's reading missing as success — or dropping missing under censoring, which is what this code does — that flatters.

**`exploration_cost` passes vacuously.** `serve` hardcodes `exploration=False`; the mechanism has no exploration. Share 0% ≤ budget 5% → PASS. A cost criterion passing because the costed thing doesn't exist should be `unsupported` ("no exploration mechanism exists to have a cost"), especially since `spend_regret` is simultaneously `unsupported` *because* exploration is missing. Two verdicts about the same absence, one pass and one unsupported, is incoherent.

**`no_false_certification` PASS is only as strong as the fabricated inputs.** Its admissibility check consumes `bound` (caller-supplied, kind unverified — Q2) and `gateway_authorised` (defaulted in `serve` — Q4), and `admissible()` never checks evidence freshness even though `evidence_expired` is in the exclusion vocabulary and section 10 (per the docstrings) makes estimates expire. Whether section 2's definition is genuinely three-part I cannot check without SCOPE; if freshness is part of admissibility, this falsifier has a blind spot. PASS over 1 decision is also formally correct for a universal claim but "3 pass / 9" in a summary over a one-line log reads far stronger than it is.

**`check_certification` skips the chosen candidate in the hiding-place scan.** An *uncertified* decision whose *chosen* candidate was itself admissible is a hiding place — the mechanism declined to certify an assignment it could have — and the `continue` on `c.id == decision.chosen` makes it undetectable. It also `break`s on the first violation, undercounting.

Nothing is reported `unsupported` that is actually computable — `bound_calibration`, `spend_regret`, `adaptation`, `genericity` are genuinely out of reach of this log, and those four write-ups are the best part of the module. The errors all run the other way: passes too thin.

## Q4. The most likely complete-looking record supporting a false conclusion

**First place: the `metered_authorised` default in `route_once`.**

```python
authorised = bool(observation.state.get("metered_authorised", False))
```

The one module family whose stated identity is "nothing defaults" defaults here. When authorisation was never observed (it's caller-supplied and easy to omit), `gateway_authorised: false` is written — a bool indistinguishable from an observation. Downstream: `check_certification` evaluates *every* candidate with `authorised=False`, so **no candidate is ever admissible**, so an uncertified assignment made while an admissible candidate existed is structurally undetectable — `default_is_not_a_hiding_place` returns PASS *because* the observation was never made. The gap does appear as a string in `gaps`, but no acceptance criterion reads `gaps`, and the field a reader trusts (`gateway_authorised`) carries a fabricated value. This is a complete-looking record, a passing falsifier, and a false conclusion, from the commonest possible operator omission.

Close second, the compound already assembled in Q2/Q3: operator passes **point estimates** as `bounds` → logged as `bound_kind="lcb"` → non-chosen candidates labeled `below_floor` without a floor comparison → `no_false_certification` PASS → "the mechanism is not broken" claimed from a log whose admissibility evidence was never what the definition requires.

Also in the loop, two integrity problems worth naming:

- **The log is append-only in bytes and mutable in meaning.** `read()` keeps the *last* outcome line per `request_id`, so appending a new outcome silently replaces a label (`labelled/False` → later `labelled/True` wins). The append-only argument for trusting criteria computed over the log does not hold.
- **`read()` dies on one corrupt line.** A crash mid-`append` leaves a truncated JSON line; `json.loads` raises; the entire log becomes unreadable, including every intact record before it. No locking either, so two concurrent writers can interleave within a line.

## Q5. Honest release or misleading one?

I cannot check the README or CHANGELOG — **neither is in the material**, so I cannot quote the offending sentence from them; I can only judge the claim as you've reported it. On that claim: **"the loop is closed" is the over-claim.** What v0.1.0 actually closes is one *turn*: observe → decide → record, composed in `route_once`. It is not a closed loop in any control or learning sense:

- nothing persists observations (`state_ref` points at nothing),
- nothing collects outcomes (`attach_outcome` exists; no code calls it),
- exploration is hardcoded off and propensity is constant, so the log can never support the off-policy estimation the loop would learn from,
- nothing feeds acceptance results or outcomes back into the policy — the arc from `record` back to `decide` does not exist.

A closed loop that cannot update anything from its own log is a pipeline. Honest phrasing: "one turn of the loop now runs end to end; the loop does not yet close."

Within the material actually provided, the sentence closest to over-claiming is in `observe.py`: **"Every reading carries its own `as_of`."** It is false as implemented (one timestamp stamped before the fetch), it makes `spread_s` — advertised as the defense against stitched-together states — permanently zero, and "**Nothing here defaults**" is falsified one module over by `route_once`'s authorisation default. The acceptance output is the *most* honest artifact here — six `unsupported` with specific remedies is genuinely good practice — but its "3 pass" over a one-decision log, with two of the three passes vacuous (Q3), is the kind of summary a reader will screenshot and misread, and `summarise()`'s careful note will not travel with the screenshot.

**Verdict:** honest in intent and unusually honest in its refusals; misleading in four load-bearing places — the fabricated exclusion reasons, the authorisation default, the pass-on-absence floor test, and the dangling state reference — each of which is exactly the class of error the docstrings were written to forbid.
