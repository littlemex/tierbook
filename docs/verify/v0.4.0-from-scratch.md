# From-scratch verification: nothing inherited on either side

**What this is testing, stated as a claim that can fail.** The standing order's third item says: *there is certainly
some part that currently works only because of ad-hoc manual setup.* So the deliverable here is not "it works" -- it is
a build that starts from the repositories alone and either runs, or **names exactly what it could not do without a hand
that is not in any repository.**

Two sides, and each gets its own clean environment rather than reusing a working one:

| side | what "from scratch" means | what is deliberately NOT reused |
|---|---|---|
| gateway | a fresh shallow clone, a **new resource prefix**, its own stacks | the existing `stratoclave-*` stacks, their DynamoDB tables, their Cognito pool, the image already in ECR |
| cluster | a **new cluster name** with its own terraform state key | the existing long-lived cluster, its nodegroups, its storage classes, anything already applied into it |
| loop | tierbook's own example, pointed at both | any hand-seeded key, table row or policy artifact |

A new prefix and a new cluster name are what make this honest. Re-running a deploy over a working environment proves
that a deploy is idempotent, which is a different and much weaker claim -- an object created once by hand goes on
existing, and the second run inherits it silently.

## What was inherited anyway, listed rather than hidden

Per `/real-machine-test`: where an existing environment must be reused, list what is being inherited and check each
item relied on.

**Since this record was written, the two gaps it found are carried as patches** in `infra/patches/`, applied to a fresh
checkout by `infra/tierbook-up` before anything deploys. The verification below describes what was done by hand at the
time, which was surgery on the deployed resources -- a change of that shape cannot be sent upstream, drifts silently when
upstream moves, and cannot answer "is it fixed yet". The diffs can and do all three.

| inherited | why it could not be built here | checked |
|---|---|---|
| the AWS account and its CDK bootstrap (`CDKToolkit`) | bootstrapping is a one-time account act, not part of either repository | the deploy script's own `check_bootstrap` gate runs against it |
| Bedrock model access for the Claude family | a console entitlement on the account, with no API to create it | named as a prerequisite in the gateway's README |
| the shared terraform state bucket | shared across clusters by design; a per-run bucket would orphan state | the new cluster writes to its **own key** under it |
| a machine with a container runtime, for the backend image | see the finding below -- the laptop's could not start | the build runs on a remote builder with `CONTAINER_CLI` |

## Findings so far

### 1. The laptop cannot build an image, and the documented one-liner requires one

`scripts/install-infra.sh` checks for `docker` on `PATH` and stops without it. This machine has Finch instead, and
Finch's VM will not start:

```
dial unix /private/var/run/finch-lima/socket_vmnet.finch-shared: connect: no such file or directory
```

That is a privileged host daemon, not anything either repository owns, so it is an **environment** finding rather than a
defect -- but it does mean the documented single-command path does not run on this host. What saves it is that
`iac/scripts/build-and-push.sh` already reads `CONTAINER_CLI`, so the image build can be moved to a host that has a
runtime without editing anything. The one-line installer does not expose the same knob.

### 2. The local quickstart's prerequisite list is a subset of what `make up` requires

The README's local-mode prerequisites name a container runtime, GNU Make, credentials and two ports. `make _host-deps`
additionally requires a host Python with `backend/requirements.txt` installed, which `docs/LOCAL.md` documents in full
and the README does not. The gate fails with the fix printed, so a reader is not stuck -- this is a documentation
inconsistency and not a broken path.

Also, on this host the system Python is 3.9 and `backend/requirements.txt` pins a FastAPI that has no 3.9 wheel, so the
host requirement is really "Python 3.11 or newer", which neither document states.

### 3. The deploy path is prefix-clean, which is what made a parallel build possible at all

`STRATOCLAVE_PREFIX` reaches the stack names, the ECS cluster and service names, and the ECR repository lookup, and
`deploy-all.sh --dry-run` printed a plan of eight stacks all named `scratch1-*`. Nothing had to be edited to build a
second, isolated copy beside the running one. This is the property that a from-scratch verification depends on and it
is worth recording as a pass rather than assuming it.

### 4. The image build assumes a host whose container config it owns

On the remote builder the push failed after a successful ECR login:

```
ERROR: open /home/coder/.docker/buildx/activity/default: permission denied
```

`~/.docker/buildx` on that shared box is root-owned, so buildx could not write its activity file. Nothing in the
repository is wrong -- `CONTAINER_CLI` did its job and the login worked -- but the documented build has no way to say
"use a config directory I own", so the fix was environment-side: `DOCKER_CONFIG` and `BUILDX_CONFIG` pointed at a
private directory. Worth recording because the from-scratch claim includes the builder, and the builder is the one host
in this exercise that is not disposable.

With that, both images built and pushed to the fresh repository: the service image and the Lambda image, the latter at
280,183,855 bytes, tagged `lambda-20260919-161303`.

### 5. The cluster module needed no edit to stand up beside a live one

`terraform.tfvars` alone -- a new `cluster_name`, a new `vpc_cidr`, the three continuously-billing storage filesystems
off, one small on-demand GPU pool -- produced a plan of **153 to add, 0 to change, 0 to destroy**. Nothing in the module
was touched, and the only messages were two deprecation warnings from a vendored VPC module. The documented
`bootstrap-remote-state.sh` adopted the existing state bucket and wrote a key derived from the new cluster's own
name, so the new cluster's state cannot collide with the live one's.

The one thing the chart's own comments made unavoidable: `gpuServingVllm.memory` defaults to 48Gi, which does not fit
the node this pool launches. The chart says so in a comment that records what happened when someone got it wrong --
eleven spot nodes launched for one replica, because the scheduler reported insufficient memory and Karpenter read that
as "add a bigger node". That comment is why this run set the value deliberately instead of discovering it.

### 6. The documented way to create the first admin cannot work, and the alternative is labelled stale

**This is the ad-hoc setup the standing order predicted, found.** The gateway has two documented paths to its first
administrator and neither is usable as written.

`docs/DEPLOYMENT.md` says: export `STRATOCLAVE_BOOTSTRAP_ADMIN_EMAIL`, redeploy the ECS stack, then read the temporary
password out of Secrets Manager. The design behind it is real and visible in the code -- `ecs-stack.ts` pre-creates the
secret with an empty value and grants the task `PutSecretValue` on exactly that ARN, and `backend/bootstrap/seed.py`
reads the variable at startup and writes the password there.

**The variable appears nowhere in `iac/lib`.** The live task definition carries 66 environment variables and no ECS
secrets, and that one is not among them. So the documented procedure runs to completion, reports success, and creates
nothing: the user pool had zero users afterwards.

| half | observation |
|---|---|
| reproduce | deploy the stacks, export the variable, redeploy the ECS stack as documented. `cognito-idp list-users` returns **zero users**. The rollout reports `COMPLETED` |
| verify | register **one** task definition revision whose only difference is that variable, and force a deployment. The pool has **one CONFIRMED user**, and the pre-created secret now holds the email and password the backend wrote |

One variable is the whole difference, which is what makes this a cause rather than a symptom.

The other path is worse. `scripts/install-infra.sh` -- the one-line install the README leads with -- calls
`scripts/bootstrap-admin.sh`, and `deploy-all.sh`'s own final output says *"bootstrap-admin.sh is stale"*. That script
works by POSTing to `/api/mvp/admin/users` with the admin-creation gate open, a route the backend's own comment calls
"the single biggest operational footgun in the current threat model". The installer does close the gate afterwards by
default, so the one-liner is not insecure by default -- but the admin it creates comes from the superseded route, and
the mechanism the code was restructured around is unreachable.

The existing deployment has an administrator. Nothing in either repository explains how it got one.

### 7. The serving chart cannot pass an engine flag, so it cannot serve what a coding agent sends

Every request the Ops example sends carries tool schemas, because that is what a coding agent sends. The served box
returned 400 to all of them:

```
"auto" tool choice requires --enable-auto-tool-choice and --tool-call-parser to be set
```

`charts/experiments/templates/gpu-serving-vllm.yaml` renders a fixed list of five engine arguments with no `extraArgs`
escape hatch, so there is no way to start the engine with those flags through the chart. The verification continued by
patching the live Deployment, which is exactly the kind of hand that is in no repository.

The finding is not "the flag was not set". It is that **an OpenAI-compatible serving chart with a closed argument list
cannot serve an agent harness**, and the two candidates a router is choosing between therefore differ at the harness
level and not only on price.

### 8. The example was conflating a refusal with a bad answer -- and the mechanism was not

The fourteen 400s came back through the loop as `accepted=False`, and the loop reported a quality result: acceptance
0.00 on the box. That reads as a model which is bad at the task, and it is a model that was never asked.

The mechanism already had the distinction -- `evidence.UNOBSERVED` with `UNOBSERVED_REASONS` including `unsupported`,
and `Cell.attempted` excludes it. The example's crude boolean did not, so the example was fixed rather than the
mechanism: `Reply` now carries `unobserved_because` validated against the mechanism's vocabulary, the loop records one
of the three states, `acceptance` divides by attempts rather than requests, and `preferred()` refuses to rank a
candidate that never served the request at all.

Worth stating plainly because it cuts both ways: on this occasion the framework was right and its first real caller was
wrong, which is the opposite of the previous three findings and is the reason the example exists.

## Reproduce / verify pairs

A pair is only evidence if the reproduce half observes the cause rather than a downstream symptom several unrelated
states could produce.

| # | claim | reproduce | verify |
|---|---|---|---|
| 1 | the gateway stands up from the repository alone | n/a -- nothing existed under this prefix | nine stacks `CREATE_COMPLETE`; a real call on `/v1/chat/completions` returned **200** with all four billed legs in `usage` |
| 2 | the cluster stands up from the repository alone | n/a -- a new cluster name and state key | `153 to add, 0 to change, 0 to destroy`, then `153 added, 0 changed, 0 destroyed`, **zero module edits**; three nodes Ready and no system pod outside Running |
| 3 | the loop runs against both and records real spend on four legs | the same loop on the base example with a fake agent | 14 live turns: box **$0.00003549** per accepted answer against the API's **$0.00077** (21.7x), four legs on every turn with the cache legs present as zero, one stable harness identity across turns, and `preferred() == box` derived from the measurement |
| 4 | throughput is **measured** rather than declared | the first probe reported a *derived* concurrency of 0.73 and `Offered` refused it outright | an in-cluster open-loop probe at four rates: **718,410/hour** completed at 200 arrivals/s, all inside an 8s deadline, p95 1.627s, 444 peak in flight against 256 seats |

Pair 4 is the one this repository has never had, and it produced two corrections rather than just a number.

**The probe's first output could not be constructed.** It reported concurrency as rate times mean latency -- 0.73 --
and `Offered` refuses anything below 1, correctly: the field means the load that was offered, and a product of two
averages is not something anybody offered. The probe now reports peak requests actually in flight.

**The vocabulary was missing the state the run was in.** The generator kept up (worst dispatch lateness 14
milliseconds), the offer exceeded the seat count (444 against 256), and the rate is *still* a lower bound, because every
one of 12,099 requests came back inside the deadline. Nothing queued, so the ceiling was never reached. None of
`generator_saturated`, `offered_below_seats` or `generator_not_checked` says that, so `UNDERSTATED_BECAUSE` gained
`load_fully_absorbed`. With it, a requirement of 100/hour is `deliverable` against this run and one of 1,000,000/hour is
`unknown` rather than `refused` -- which is the whole point of recording it.

And the number the cost side has been waiting for since F131: at $2.699/hour for the instance and 17.78 Mtok/hour
measured, the box costs **$0.1518 per output Mtok**, an *upper* bound on price because the rate it divides is a lower
bound on throughput.

## Running the whole thing as one command, and the four defects that only that found

Everything above was verified in pieces. The claim that **one command brings the candidates up** was not, and running it
found four things no test had.

### 1. The image has to exist before the service that pulls it

A fresh deploy hung. The ECS service cannot place a task whose image is absent, so it never reaches a steady state and
CloudFormation waits on it for hours, with the reason visible only in the service's events
(`CannotPullContainerError ... not found`). Deploying every stack and then building the image -- which is the order the
gateway's own installer uses -- therefore only works when a previous run left an image behind.

Fixed by deploying the registry stack alone, pushing the image, and then deploying the rest. A test pins the order by
position, because the alternative is a paid deployment per assertion.

### 2. A gateway prefix is single-use, and the second run said so eight minutes in

Several of the gateway's resources are retained on purpose when its stacks are destroyed -- the registry, the DynamoDB
tables, the bootstrap-admin secret -- because they hold data. A `create` with the same prefix then fails partway through
on the first of them. It failed twice in a row this way, each time after the image build.

Now listed and refused up front, by the same function `doctor` uses, naming every retained resource found and the two
ways forward. Deleting them is the operator's decision: what survives a teardown here is exactly the data somebody chose
to keep.

### 3. The config file was read after the paths derived from it

`TIERBOOK_WORK_DIR` set in `config.env` was ignored, because the work directory was computed two lines above the line
that sourced the file. A run wrote its state, its checkouts and its connection file somewhere the operator had not asked
for, silently. The config is now read before anything derived from it.

### 4. A box in overload was priced as if it were a measurement

The probe ran at the configured 96 arrivals a second. The box completed **189 of 5,680** requests, 40 of them inside the
deadline, at a p50 latency of 17 seconds -- a box being crushed. From that the script derived **$18.29 per output Mtok**
and wrote it into the connection file with no flag, because the run passed every honesty check the throughput module
has: the generator kept up, and the offered concurrency exceeded the seat count.

The signal was there and nothing was reading it. A run whose goodput is a fifth of its completed rate is a queue being
measured, not a box, and a per-token price divided out of it is an artifact. `measure` now refuses, printing the three
counts that produced the refusal and the one knob that fixes it. At 8 arrivals a second the same box completed 463 of
463 inside the deadline and priced at **$4.0070 per output Mtok, flagged as an upper bound**.

### What the run then demonstrated, which is the point of the whole framework

| | measured at 200 arrivals/s (box full) | measured at 8 arrivals/s (box mostly idle) |
|---|---|---|
| box price per output Mtok | $0.1518 | $4.0070 |
| box spend per accepted answer | $0.00003549 | $0.00093873 |
| API spend per accepted answer | $0.00077000 | $0.00077000 |
| **what the loop preferred** | **box** | **api** |

Same code, same policy, same two candidates, opposite answers. Nothing in the mechanism changed and nothing was tuned:
the price of a fixed-cost candidate depends on how full it is, and the loop read the number it was given. Both runs
carried their provenance -- the derived price says it is an upper bound when the throughput behind it is a lower bound,
the capacity says `deliverable` for the box and `unknown` for the metered arm -- so which number produced which answer is
recoverable from the record rather than from memory.

This is the clearest evidence in this repository that the measurement is the input and not the conclusion.

## The teardown, checked rather than assumed

A verification that leaves a bill behind has a defect of its own, so the destruction is evidence too:
`Destroy complete! Resources: 153 destroyed.` for the cluster, zero stacks left under the gateway's prefix, the
pre-existing cluster alone in the region afterwards, and no instance still carrying this run's tag.

The cluster module's own drain guard is worth recording because it behaved exactly as its comments promise. It held the
destroy for thirteen minutes waiting on Karpenter's node-class finalizers, then force-cleared them -- which it documents
as safe only after the hard gate has proved no backing instance exists -- and finished by asking the **cloud provider's
instance API**, scoped by tag, whether anything was still running.

To be exact about what that check is and is not: **deployment here is Kubernetes only.** A Karpenter-managed worker node
*is* a cloud instance underneath, and the failure this guard exists to catch is precisely the one where the Kubernetes
object disappears while the instance it stood for keeps running and billing. Kubernetes cannot see that state -- the
object is gone, so there is nothing left to list -- which is why the last check reads the instance API instead. It is a
billing assertion about nodes the cluster owned, not a second deployment target, and nothing in this verification runs
anywhere other than on the cluster.

## What was not verified

- **The local `make up` path.** The laptop's container VM will not start, and the fix is a privileged host daemon. The
  gateway was verified deployed instead, which is the stronger check, but the local path remains unexercised here.
- **The gateway's own quota-gated stacks.** `deploy-all.sh` names a required second pass for the quota reconciler and
  grants, and this run did not make it. What that leaves unverified is stated in the deploy output itself: limit-raise
  grants that never expire, and tenant pools that vanish on the first of the month.
- **The cluster's storage layer.** FSx, OpenZFS and EFS were switched off deliberately, to avoid a continuously billing
  filesystem outliving the verification. Nothing here says they stand up from scratch.
- **Contention on the ledger.** The property the gateway cares most about is its behaviour under real concurrent
  settlement, and fourteen sequential turns do not touch it.
